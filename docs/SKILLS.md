# 自创人物、限定心象与技能积木

## 一、设计者怎样使用工坊

1. 在“心象工坊”载入一个示例，先修改构筑名、人物名、称号和系列。
2. 选择颜色、4～7 的体力、插画与可选异色翻面。冷暖可互为另一面，无色暂不支持翻面。
3. 人物最多两个技能。每个技能选择时机、条件、手牌/心象代价，并添加一至三个效果积木。
4. 编排十三张心象。每个点数 A～K 各一张，通用类型只能从该点数原帖两个系列的候选中选择，或使用限定心象。卡位的先后就是从牌顶到底的取用顺序；改变牌型不会改变点数。用移动按钮调整先后。
5. 将某个位置设成限定心象时，填写卡名、限定系列、非该系列时视作的普通牌和效果积木。一副至多四张限定牌。
6. 执行服务端校验，阅读生成的规范效果说明和预算。如果超限，降低数值、增加合理代价或减少效果。
7. 保存后，在允许自创的房间中选择它。已开始的对局保存了旧快照，不会被工坊中的更新影响。

普通用户全程不需要写 JSON。高级导入、导出用于分享、备份和开发，不能突破服务器验证。文本卡名与说明只用于展示；改名不会得到同名普通牌的规则能力。

## 二、执行模型

```text
可视化字段
    ↓
结构化构筑（人物 + 技能列表 + 有序心象）
    ↓
Rules::validateBuild 严格类型、白名单、数量和预算校验
    ↓
房间开局快照
    ↓
Engine::act 认证席位、时机、费用、目标和次数核验
    ↓
有限积木解释器执行，结算伤害/心坏/退场/胜负
    ↓
只向客户端返回该席位可以知道的视角
```

后端没有 `eval`、用户脚本、SQL 积木、文件访问或 HTTP 请求积木。创作者提交的是数据，不能提交 PHP/JavaScript 回调。积木集合是刻意有限的 MVP：它覆盖常用原型，不宣称任何自然语言技能都能自动实现。

## 三、现有积木的语义

### 时机与次数

| `trigger` | 时机 | `target` 的关联角色 |
| --- | --- | --- |
| `active` | 自己的出牌阶段主动使用 | 由玩家选择一名存活角色 |
| `turn_start` | 自己的回合开始 | 自己 |
| `after_damage` | 自己实际受到伤害后 | 伤害来源；无来源时按引擎默认关联处理 |
| `after_attack` | 自己使用攻击实际造成伤害后 | 受到攻击伤害的角色 |
| `on_defend` | 自己成功防御后 | 攻击来源 |

首版固定 `limit: 1`，含义是**每个全局回合最多一次**，不是“每轮每位角色都行动一次”才刷新。被动满足条件且费用可支付时自动执行；手牌费用自动从当前手牌左侧支付，心象费用从牌顶支付。主动技能可指定手牌代价。这个自动被动裁定减少网络询问窗；代价较大的可选技能，建议先做成主动技能。

所有人物技能在心坏时关闭。技能伤害仍可能引发其他角色的受伤技能，但每项技能在支付与结算前就记为本回合已用，且单动作有96个事件/效果的硬上限；不能靠“受伤→再伤害→再受伤”无限循环。效果按列表顺序执行，前一项导致退场、胜负或心坏时，后一项仍需遵守存活、治疗和区域约束。

### 条件

| `condition` | 判断 |
| --- | --- |
| `always` | 无额外条件 |
| `wounded` | 当前有效精神低于当前身体上限 |
| `hand_low` | 手牌不超过两张 |

条件在技能尝试发动时检查，不能在前端自行判定为真。代价为 `cost.hand` 和 `cost.mind`，各允许 0～2。后端检查是否足够后才支付。一次发动的积木不会逐项重复收取费用。

### 效果

各效果 `amount` 为整数 1～3。`target` 只允许 `self` 或 `target`。

| `op` | 执行 | 目标限制 |
| --- | --- | --- |
| `draw` | 摸指定数量普通牌；用尽时回收普通弃牌 | 自己/关联角色 |
| `heal` | 回复精神；不能超过身体上限，心坏不能回复 | 自己/关联角色 |
| `damage` | 造成指定颜色的直接技能伤害 | 自己/关联角色 |
| `recover_mind` | 从自己的已耗心象回收到心象底 | 只能自己 |
| `shield` | 获得暂时护盾，抵扣后续伤害 | 自己/关联角色 |
| `range` | 本回合增加攻击范围 | 只能自己 |
| `attack_bonus` | 本回合增加攻击伤害 | 只能自己 |

颜色字段 `color` 只能是 `cool`、`warm`、`neutral`；非伤害积木仍会规范化这个字段，但其颜色不产生作用。伤害积木属于**技能直接伤害**，不是一次普通攻击，不会自动提供《防御》响应窗。直接伤害因此具有较高预算；制作攻击型技能时务必理解该区别。系列模式仍将其处理成普通伤害。

此版不能通过组合积木任意查看对方手牌、偷看未来普通牌、改变回合拥有者、修改普通牌池、修改胜利条件、插入无限新技能或制造任意卡牌。判定目前是《加速》《飞来横祸》《意外之喜》等锁定卡的能力，未向创作者开放通用条件分支积木。

## 五、内置示例怎样拆成积木

| 人物/卡牌 | 范式 | 对应结构 |
| --- | --- | --- |
| 澄页·拾遗 | 受伤获益，类似桌游常见“受伤摸牌” | `after_damage → draw self 1` |
| 澄页·校订 | 手牌换循环资源 | `active + 手牌1 → recover_mind self 1` |
| 烬途·余焰 | 命中追伤，以有限心象作代价 | `after_attack + 心象1 → damage target 1 warm` |
| 烬途·远行 | 开始阶段距离优势 | `turn_start → range self 1` |
| 无相·返场 | 防守补偿 | `on_defend → draw self 1` |
| 无相·换幕 | 有条件的整备 | `active + wounded + 手牌1 → draw2, heal1` |
| 苔序·预装甲 | 周期防御资源 | `turn_start → shield self 1` |
| 苔序·超频 | 手牌换当回合攻击收益 | `active + 手牌1 → attack_bonus self 1` |
| 记忆的索引 | 顺序执行抽牌、治疗、回收 | `draw2 → heal1 → recover_mind1` |
| 落日余温 | 限定系列进攻牌 | `damage target warm1 → draw self1` |
| 换幕的面具 | 资源与防御复合 | `draw2 → shield1` |
| 庭园蓄电池 | 进攻准备 | `range2 → attack_bonus1` |

这些示例借鉴的是《三国杀》《BANG!》等牌类游戏中常见的交互范式，名称、人物和插画为本项目原创。原帖的金海鸣、红暮、丁香包含窥视重排、跨人交换、卡牌转换、心坏特殊觉醒等复杂机制，当前没有将其原技能伪装成已经实现；可用后述扩展流程逐一加入。

## 六、强度预算的具体公式

人物上限 18，限定牌合计上限 24，单张限定牌上限 12；这三条分别核验，不能用另一区域的剩余预算补贴。

- 初始体力预算：`(hp - 4) × 2`。
- 允许一次异色翻面：额外 2。
- 每个技能：各效果预算之和，被动时机加 2，再减 `min(4, 手牌费用 + 2 × 心象费用)`，最低为 1。
- 每个效果：摸牌2、治疗2、伤害4、回收心象3、护盾2、范围1、攻击增伤3，乘以数值。
- 无色伤害每点额外加 1。
- 限定心象没有技能费用折扣，直接合计效果预算。

条件当前不减预算，防止把几乎总能满足的条件写成免费强度来源。角色最多2技、单组最多3个效果、最多4张限定牌、点数唯一和数值范围也是独立限制。强度预算不是统计估值：系列限定对本系列角色没有实际成本，回复与回收存在组合收益，控制与直接伤害在不同人数下的价值不同。内测应分别收集模式、人数、座位、角色版本、开局顺序和胜率。

## 七、开发者怎样增加一个积木

后端 PHP 是规则权威。增加前端下拉选项不能令服务器自动理解新效果；增加服务器白名单但不提供执行器也不算实现。

以增加 `discard_target`（指定目标弃置手牌）为例，先明确它是随机弃牌、目标选择，还是来源指定公开牌。不同选法意味着不同响应窗与隐藏信息风险。建议先做“目标随机弃一张”的有界版本：

1. 在 `src/Rules.php` 的效果白名单加入新操作，定义合法目标和数值上限；同时更新 `effectCost`，不能默认为0。
2. 在 `src/Catalog.php` 的 `blocks.effects` 中增加中文名称，提供目标限制与规范解释。
3. 在 `src/Engine.php` 的效果分派处实现：确认目标存活、手牌非空；使用服务器随机源选择；通过统一区域移动/弃牌函数处理普通牌与心象归属；不可直接将其塞进公共弃牌堆。
4. 如需要玩家选牌，必须创建新的 `pending` 响应类型、期限、默认动作和仅对该玩家可见的选择列表；不得把对方全部手牌发给来源以便前端过滤。
5. 更新工坊效果选项、描述与目标提示；前端约束是体验优化，后端仍完整校验。
6. 增加规则测试：无牌、心象牌归属、目标死亡、心坏、非法数值、错误席位响应、重复请求、超时、与现有效果的组合。
7. 提高 `rulesVersion`，为旧构筑提供显式迁移或拒绝导入提示；已开始的旧局先结束，不混跑两版解释器。

“高级设计者制作积木”可进一步做成**白名单基础效果的命名组合/宏**，发布时展开并重新验证总节点、预算和递归深度。不要允许高级设计者上传 PHP、JavaScript、SQL 或表达式 `eval`。当前只提供开发者修改源码扩展，不提供在线发布新操作码。

## 八、改造原稿中的复杂技能

- **信息嗅探**：需要一个“私密查看”视图和一个只允许排列原牌 UID 集合的重排动作。校验排列前后多重集合相等、只能作用于牌顶最多五张；公共日志只记录查看/重排发生，不记录内容。
- **信息交易**：需要跨玩家的明确选择窗，支付、取牌与返还作为一次事务，所有心象实体保留归属；超时有可支付的默认返还方案，不能取完牌后断线逃掉返还。
- **装甲运用**：不要用改卡名完成转换，增加“以某种规则类型使用”的动作，白名单限定来源区域和可转换类型；保留实体 UID 和原始归属。
- **红化：服从**：需要心坏状态变化事件和“每局一次”计数器；觉醒监听必须明确能否在技能被心坏停用前触发，防止重置心象再次触发自身。把它作为引擎明确支持的特殊时机后再开放，不能简单沿用普通受伤触发。

## 九、API 使用与故障定位

普通前端使用 JSON POST 到 `api.php?action=...`，认证头为 `Authorization: Bearer <访客凭证>`。不要把凭证放进查询参数。修改对局时提供当前房间 `revision` 与唯一 `requestId`；同一请求重试必须保留原 requestId 和原载荷。409 表示状态或请求发生冲突，应刷新并重新决定动作。

构筑验证入口 `validate_build` 与保存入口 `save_build` 都会执行同一规则验证。自动测试可直接调用 `Rules::validateBuild`，但生产写入应走 API 所有权检查。禁止设计者通过上传文件覆盖服务器 `Catalog.php`。

排障顺序：验证定义 → 检查时机/次数/心坏 → 检查费用和目标 → 查看公共日志 → 导出已结束对局。进行中的导出仅包含调用者视角，不应拿它当上帝视角回放。首次扩展建议只改一个操作码，保留可复现构筑文件及失败动作。
